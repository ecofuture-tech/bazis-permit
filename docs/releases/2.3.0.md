# bazis-permit 2.3.0

Requires Bazis 2.3 (Django 6.1, FastAPI 0.142) and bazis-users 2.3.

## Security

- **Related objects of created and changed items.** New setting
  `BAZIS_PERMIT_RELATIONS_VIEW_CHECK` (off by default, recommended): a created or changed
  item can reference only the objects of permission-protected models that the user can
  view; otherwise the request fails with 403 `ERR_RELATION_ACCESS`. Without it, a user who
  can add, for example, dependent entities could attach them to parent entities of other
  users that they cannot see. Only newly referenced objects are checked; a route can
  override the setting with `relations_view_check`. This resolves the TODO of the package
  together with `check` permissions (see the README, "Related Objects").
- **Cache of the role permissions.** It was invalidated only for many-to-many changes made
  from the side of the role or the group: a group added to a role from the side of the
  group, a permission added from the side of the permission, a renamed permission, a
  deleted group or permission kept the old permissions until the cache expired. Any change
  of roles, groups, permissions or their relations now invalidates the cache of all roles
  (a version in the cache keys). A role without permissions is cached too.
- **Selector permissions of anonymous users** (e.g. `view.author` in the role for anonymous
  users) failed with 500 (`"__selector__" is not a valid UUID`); they now match nothing. A
  permission with a selector the model does not have matches nothing and logs a warning.
- **XSS in the admin:** the list of users rendered role names as HTML.

## Fixes

- A retrieve request with sparse fieldsets and `include` failed with 422: the response
  schemas of permission routes used the request resource schemas, in which fields are
  required (the same fix as in Bazis 2.3 for routes without permissions).
- `is_model_permit` no longer fails for models without a JSON:API route.
- Migration `0007_name_en_blank`: `0006` renamed `name` to `name_en` without its new
  attributes (`blank=True, default=''`), so `makemigrations` created a migration inside the
  installed package. It does not change the database.

## Other changes

- The sample project referred to a non-existent `bazis.contrib.permit.urls`, so Django
  system checks failed; its migrations are brought in line with the models. The `test`
  extra installs bazis-author, which the sample project uses.
- Dependencies: `bazis>=2.3.0`, `bazis-users>=2.3.0`.
- CI runs the tests on Python 3.12–3.14 and with the lowest allowed dependency versions and
  checks for missing migrations; releases are made with the Release workflow
  (see `CLAUDE.md`).
