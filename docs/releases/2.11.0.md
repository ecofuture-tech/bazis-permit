# bazis-permit 2.11.0

Requires bazis 2.16.

## Breaking changes

- **Custom actions declare who may call them.** A custom action of a `PermitRouteBase` (a
  route of kind `other`: the `http_*` decorators without `kind=`, not the internal route) is
  checked in `route_check` of the core, before it runs:
  - `public=True`: anyone, limited by `BAZIS_THROTTLE_PUBLIC` of the core (per user or IP
    address);
  - `access_action=`: the roles decide, also those for anonymous users; an action of the
    collection needs the permission on the model (403), an action of an item on its item,
    which bazis-permit takes by `item_id` into `self.item` before the action runs (404 for
    an item the user cannot view, 403 without the permission), locked for POST, PUT, PATCH
    and DELETE so that the permission checked holds while the action runs;
  - neither: authenticated users only, an anonymous user gets 403 `ERR_FORBIDDEN` (as on a
    create or an update), whatever the roles for anonymous users.

  The item of such a write action is locked `FOR NO KEY UPDATE` for the whole action, so
  long actions on the same hot row wait for each other.

  The `/_id/` route of the core declares `access_action=view`: it is open as `GET /`, also
  to the roles for anonymous users.
- **The selector arrays are not in the schemas.** The generated fields
  `autogen_<field>_selectors` (`autogen_selectors_fields`) were attributes of every route
  of the model and of its objects in `included`: a client read the ids in them and a user
  who may change an object (or create one) could write the id of another user into an
  array, which gave that user the permissions of the selector (`author`) on the object.
  `PermitModelMixin.get_fields_hidden()` (bazis 2.16) leaves them out of the default
  schemas: a write with them is 422 `ERR_VALIDATE`, a `filter` or a `sort` by them is 400.
  They still select the objects for the permissions; the project fills them (or the
  admin). A route that shows one names it in `include`; the `exclude` of a route that
  removed them can go.
- **`permit.W004` is removed.** The untranslated names of the declared roles and groups
  are listed by `manage.py bazis_messages status` of the core; the check printed them on
  every command, also into the JSON of `bazis_messages`.

## Changes

- **`permit.W007`**: a custom action, of the collection or of an item, that declares
  neither `access_action` nor `public` (open to every authenticated user); `public=False`
  declares that intent.
  The check needs the loaded application, so `manage.py bazis_doctor` reports it, not a
  plain `manage.py check`: run `bazis_doctor` after the upgrade.
- **The meta field `custom_actions`** (`?meta=custom_actions`): the names of the custom
  actions (`action` of `x-bazis`) the user may call, by the rule of `route_check`
  (`PermitRouteBase.action_allowed`): on an item the actions of an item on it, on a list
  the actions of the collection. A client shows the buttons of the actions from it instead
  of a meta field of the product.
- The guide describes the custom actions (the gap "public own action") and an operation of
  its own (a subclass of `AccessAction`).
- The helpers of the declarations (`discover`, `lock`, `migrations_complete`, the managed
  objects taken over by a declaration and `ManagedAdminMixin`) moved to the core,
  `bazis.core.declare` and `bazis.core.admin_abstract` (bazis 2.16), shared with
  bazis-statusy and the schedules of bazis-bg; `bazis.contrib.permit.declare` still gives
  `discover`, `lock` and `migrations_complete` for bazis-statusy < 2.12. The warning of a
  declaration that takes over an object is logged by `bazis.core.declare`.

## Deprecations

- `bazis.contrib.permit.declare.untranslated` is kept for bazis-statusy < 2.12, which
  imports it, and warns (`DeprecationWarning`); it is removed in bazis-permit 2.12.
